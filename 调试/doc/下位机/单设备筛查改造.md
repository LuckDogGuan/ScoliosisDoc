# 单设备筛查：下位机实施契约

## 连接与语音

专用路由器、一台电脑是本轮使用前提。设备 `hello` 与配对、解除事件携带 `event_id`；只有电脑明确接收并收到板端回执，界面才显示“仪器已确认”。断开与 Wi-Fi 掉线分开：断开不等于无线断网。录制期间不插播。

使用“晓晓”同一音色：现有 `capture_done`、`uploaded`、`saved_on_device`、`storage_low`、`capture_failed`、`please_connect`、`pair_success`、`pair_failed` 八句，加同音色 `wifi_connected`、`wifi_disconnected`、`pair_disconnected` 三句。只在对应状态边沿播报，同一句 30 秒内限频。`pair_failed` 仅在设备收到明确拒绝或已接到请求后超时时触发；电脑完全无法联系设备时，板端不可能播报电脑上的失败。当前无主电池和电量计，不播报或上报虚构电量。

## 拍摄与上传

主控制循环负责唯一录像任务，后台上传工作者最多一个，顺序读取 `pending` 中完整 MP4；上传失败留片并退避重试。录制成功且文件进入 `pending` 后便可接下一个学生的命令，上传不占用录像锁。开录前检查 `/userdata` 空间，至少保留系统余量和一段录像的预估上界；空间不足拒拍，但不能删除待传片。回执必须含相同 `capture_id`、长度与 SHA-256；回包丢失先查询回执，不盲目重传或删片。掉电后扫描待传目录恢复上传；未收尾的 `writing` 与 `video0` 文件保持隔离、等待人工核对。

每次拍摄向电脑报告实际阶段：`recording`、`pending_local`、`uploading`、`stored` 或 `failed`，不能仅依赖电脑按时间推测。设备资源上报增加 `/userdata` 总量、`MemAvailable`、`MemTotal`，RSSI 保留 dBm。电池仍是 `absent`。遥测失败应报未知，不能填 0 或沿用旧值伪装实时。

## 本轮风险与实板验收

UDP 发现仍可能被同网段主机诱导改变电脑地址；HTTP 仍无设备验签、无 TLS。本轮依赖专用、有密码的局域网，不宣称已消除接管、伪造或窃听风险。后续再设计设备凭据与加密。录制和上传重叠必须在真实板上检查十秒片时长、实际帧数、文件哈希、音频播报与网络恢复；若并行导致帧数或录像质量下降，调低上传占用后重测，不能把代码并发视为实板通过。
