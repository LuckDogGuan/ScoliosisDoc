## 原生 rkipc 按需录像

`rkipc` 提供 UNIX socket `/var/tmp/rkipc`，上游代码见同目录 `_upstream_tmp/socket_server_server.c` 和 `storage_storage.c`。使用原生 muxer 的 `rk_storage_record_start` / `rk_storage_record_stop`，不需要重启 rkipc，也不需要 ffmpeg 二次封装或第二个编码进程。`storage.0:enable=0` 时按需接口仍可录 MP4；不要打开自动循环录像。

最小复现使用 `_upstream_tmp/rkipc_call.py`（仅调试使用，产品 C 程序应直接调用 socket）：

```sh
python3 /tmp/rkipc_call.py rk_storage_record_statue_get n=2 # 预期 [0, 0]
python3 /tmp/rkipc_call.py rk_video_set_frame_rate 0 s=60/2
python3 /tmp/rkipc_call.py rk_video_set_max_rate 0 4000
python3 /tmp/rkipc_call.py rk_video_set_gop 0 30
python3 /tmp/rkipc_call.py rk_storage_record_start
sleep 10
python3 /tmp/rkipc_call.py rk_storage_record_stop
python3 /tmp/rkipc_call.py rk_video_set_frame_rate 0 s=60/6
python3 /tmp/rkipc_call.py rk_video_set_max_rate 0 640
python3 /tmp/rkipc_call.py rk_video_set_gop 0 10
```

实际使用 `_upstream_tmp/capture_probe.py` 的 `finally` 恢复参数，防止中途异常留下 4000 kb/s。新片录制时，`record_start` 返回 0 耗时 0.001 秒；单调时钟经过 10.003 秒后 `record_stop` 返回 0 耗时 0.002 秒。`record_stop` 内同步执行 `rkmuxer_deinit(0)`；其返回后立即运行下列命令，MP4 可正常读取：

```sh
ffprobe -v error -show_entries format=duration,size,format_name -show_entries stream=codec_name,width,height,r_frame_rate,avg_frame_rate,bit_rate -of default=noprint_wrappers=1 /userdata/video0/20260927113829.mp4
```

Cursor 中断前留下的旧片也经 ffprobe：HEVC 1280×1080，10.734 秒，5,252,910 字节，平均约 29.25 fps。新片更接近固定 10 秒。测试后查询录制状态 `[0, 0]`、码率 `[640, 0]`、GOP `[10, 0]`，ini MD5 未变。

socket 协议：连接后读 little-endian int32 `hello=0`，再写 int32 函数名长度（含尾部 NUL）与函数名。设置帧率随后写 int32 通道号 0、int32 字符串长度（含 NUL）、`60/2\0`；设置码率/GOP 随后写 int32 通道号 0、int32 值；start/stop 无附加参数。函数 handler 返回 int32 错误码 0；服务线程之后还会写一个 int32 0。读取帧率返回长度（不含 NUL）、字符串、错误码；读取码率/GOP 返回 int32 值、错误码。每次调用开新连接即可。

`rk_storage_record_start` 按板上本地时钟的秒生成 `/userdata/video0/YYYYMMDDHHMMSS.mp4`。同秒再次 start 可能复用文件名并覆盖，产品程序需先确认录制状态和路径未占用、每次只允许一段录像，录后比对目录只接受唯一新 MP4。`record_path` 在 rkipc 初始化时由 `storage:mount_path` 和 `storage.0:folder_name` 确定，目前没有实证的动态修改接口。文件收尾后再移动至 `/userdata/capture/pending/`；移动前后都不能删除其他视频。预览客户端在录像期间应关闭；当前 rkipc 的 RTSP 服务本身无需重启，应用层还需保证不会同时有人持续观看预览。

### RTSP 仍能在录像期间拉流

录制开始约 2 秒后，用 ADB 转发 `tcp:8554 → tcp:554`，电脑现成 `调试/工具/rtsp_fps_probe.py` 对 `rtsp://127.0.0.1:8554/live/0` 完成 OPTIONS、DESCRIBE、SETUP、PLAY，3 秒收到 **96 帧、1050 包**（探针算得约 32.3 fps）。同时板端完成另一段 10.006 秒录像并恢复参数。故只调用 storage start/stop **没有停止 RTSP 推流**，设计所写“正式 10 秒不推流”尚未达成。rkipc socket 已知命令表没有单独的 RTSP pause/stop；`rk_video_restart` 会同时重启视频链路，不作为未经核对的录制中控制方案。现阶段关闭电脑 VLC 预览客户端可避免本电脑主动拉流，但这不等于服务被关闭。测试片 `/userdata/video0/20260927114206.mp4` 保留。

## BusyBox wget 上传陷阱

Wi-Fi：板上 `wlan0=192.168.0.66/23`，电脑 WLAN `192.168.0.20/23`，`wpa_cli -i wlan0 signal_poll` 显示 RSSI -66 dBm。板 ping 电脑两次均失败，但电脑临时监听 `0.0.0.0:18080` 后，板端 HTTP POST 可达；未改防火墙。测试监听已关闭，18080 已释放。

板上 BusyBox v1.36.1 的 `wget` 支持 `--post-data`、`--post-file`、`--header`、`-S`，但其 `--post-file` 对含零字节的文件不安全。复现命令：

```sh
printf abc >/tmp/wget_text_probe
printf '\000abc' >/tmp/wget_binary_probe
wc -c /tmp/wget_text_probe /tmp/wget_binary_probe # 3、4
wget -S -T 20 -O - --post-file /tmp/wget_text_probe http://192.168.0.20:18080/text
wget -S -T 20 -O - --post-file /tmp/wget_binary_probe http://192.168.0.20:18080/binary
wget -S -T 20 -O - --post-file /userdata/video0/20260927112451.mp4 http://192.168.0.20:18080/upload
```

| 文件 | 板上大小 | 电脑收到 `Content-Length` / 正文 | wget 结果 |
| --- | ---: | ---: | --- |
| `abc` 文本 | 3 B | 3 / 3 B | HTTP 200，退出码 0 |
| 首字节 NUL 的探针 | 4 B | 0 / 0 B | HTTP 200，退出码 0 |
| 旧 MP4 | 5,252,910 B | 0 / 0 B | HTTP 200，退出码 0 |

`--post-file=/path` 形式对 MP4 同样发送 0 B。可见仅凭 wget 退出码和 200 判断上传成功会丢片。JSON 小报文可用 wget，MP4 必须由产品 C 程序以二进制安全的 HTTP POST 发送，显式写 `Content-Length` 并核对电脑回包；电脑端应拒绝空正文。原设计第 8 节的“板上只用 wget 上传”这一点需要按实测修正。

用于 JSON 的准确形式另测：`/usr/bin/wget -q -T 5 -O /tmp/wget_json_reply --header 'Content-Type: application/json' --post-file /tmp/wget_json_probe http://192.168.0.20:18080/api/v1/hello`，14 B 文本 JSON 全部收到；电脑见 `Content-Type: application/json`、`Content-Length: 14`、正文 14 B，wget 退出 0，回包文件为 `{"ok":true}`。该测试监听也已关闭。

本地 `调试/声音/` 的 8 条 WAV 与板上 `/userdata/sounds/` 逐一 MD5 相同。板上已有 `wifi_connected.wav`、`wifi_disconnected.wav`，哈希相同所以未覆盖；本次只补了其余 6 条。`capture_done.wav` 为 PCM s16le、22050 Hz、单声道、16 bit；执行 `aplay -q -D plughw:0,0 /userdata/sounds/capture_done.wav` 退出码 0。软件是否在正确时机播放还须端到端验证。

`amixer -c 0 cget name='DAC LINEOUT Volume'` 原值 30（范围 0–30）；`amixer -c 0 cset name='DAC LINEOUT Volume' 30` 返回 0，复查仍为 30。

2026-09-28 按用户新要求暂调至 **10**：`amixer -c 0 cset name='DAC LINEOUT Volume' 10` 返回 0，随后 `cget` 读回 `values=10`。WSL 样例配置、板上 `/tmp/instrument_config.json` 和持久目录 `/userdata/instrument/config.json` 的 `audio.volume` 均为 10；板上业务配置执行 `--check-config` 返回 `config OK`。在音量 10 播一次 `capture_done.wav`，`aplay` 退出码 0，混音器仍读回 10；主观响度尚待用户试听，后续可改配置。
