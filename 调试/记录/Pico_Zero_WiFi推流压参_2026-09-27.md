
## 为什么往低码率收

帧率已经按 `60/2` 真正降到大约 30 之后，Wi-Fi 仍然断。断的方式没变：关联还在，板子到网关的 ping 失败，RTSP 跟着停。普通 TCP 的 iperf 以前能到约 4 Mb/s，所以不是链路完全没有带宽，而是视频的突发把 AIC8800 的数据通路堵住。

于是同时做了三件减小突发的事，而不是再改传感器驱动：

| 项 | 从 | 到 | 原因 |
| --- | --- | --- | --- |
| `max_rate` | 1024，再试 384，再到 256 | 256 kb/s | 码率越高，停得越快 |
| `stream_smooth` | 50 | 100 | 让 CBR 少突发 |
| `gop` | 30 | 15 | I 帧更密、单帧更小 |
| `enable_motion_deblur` | 1 | 0 | 去掉额外编码负担 |
| 省电 | 开 | `iw dev wlan0 set power_save off` | 只在内存里，重启要再设 |

分辨率保持 1280×1080，H.265 CBR，ISP 帧率 60，目标 `60/2`。`iw` 不支持改 legacy 速率（返回 Operation not supported），HE 速率限制没有做成。把传感器 `vertical_blanking` 从 120 调到 1322（按像素时钟估算约 30 fps）后，RTSP 计数几乎不变，随即改回 120，避免和编码器假设的 60 fps 输入不一致。

## 256 kb/s 的证据

电脑 `192.168.0.20` 用 RTSP TCP 拉 `192.168.0.66:554`。编码器日志：

```text
fps fix [60/1] -> fix [60/2] gop i [15]
bps [240000:256000:272000]
```

| 检查 | 结果 |
| --- | --- |
| 第一次拉流 | 3157 个 RTP marker / 89.92 秒，计数约 35 fps，没有中途停 |
| 结束后立刻再拉 | 281 个 marker / 7.91 秒，计数约 35 fps |
| 同期网关 ping | 日志末尾仍是成功应答；结束后再 ping 2 次，0% 丢包，约 3～5 ms |
| 信号 | 大约 −53～−59 dBm，`ChinaNet-7HrK` |

384 kb/s 的对照：第一次约 57 秒（912 个 marker / 25.92 秒那次是 26 秒窗口拉满；60 秒窗口里网关在后段开始全丢）。结束后第二次连接超时，网关 ping 全丢。所以 384 不能当连续预览参数。

RTP 计数在 256 kb/s 时约 35，在 2 Mb/s 时约 31。编码器目标仍是 30。低码率时 marker 略多，不能把 35 写成新的目标帧率。

## 现在留下的状态

`rkipc` 当时用 256 kb/s 在跑。省电为 off。网关 ping 通。副本在 `../配置/rkipc.ini.稳定-256kbps-30fps.ini`。

随后用 VLC 看 256 kb/s 时出现两件事：网关 ping 再次全丢，VLC 报无法连接 `192.168.0.66:554`；画面一动就糊，因为 1080p、30 fps、256 kb/s 时每帧大约只有 1 KB。

画质优先改为 15 fps、512 kb/s（`dst_frame_rate` = 60/4，gop 15，其余平滑和去模糊不变）。USB 计数约 18 fps。Wi-Fi 拉流 40 秒、702 个 marker，结束后网关 ping 仍通。VLC 已用 RTSP TCP、缓存 1000 ms 重新打开，连接为 Established。当前数字以 `../基础信息/推流参数.md` 为准。
